# CTP 会话语义与重建：为什么"保持会话"做不到，该建什么

> 面向：要继续改 CTP 这条线的人。这是**设计文档**（问题 + 方案 + 路线图）。
> **2026-10-29：§3 的状态机 + epoch、§4 的「未 Ready 拒绝写入」、§4.3 的在途动作对账（撤单重放 / 孤儿单清理）已实现**，
> 落点与剩余项见 §11（实现状态表）；本文其余部分仍按设计稿阅读。
> 现状缺陷复盘：`session-reauth-after-reconnect.md`；前置侧的 240 强制断连：`../../aether-ctp-hosts/doc/two-bots-live-market.md` §2.2；直连旁路（临时处置）：`../../aether-ctp-hosts/doc/direct-bot-bypass.md`。

## 0. 结论先行

| 直觉 | 实际情况 |
|---|---|
| "登录不持久" | 不是持久性问题。CTP 的**会话绑定在 TCP 连接上**，连接一断，柜台就把这条会话回收了；客户端手里那对 `FrontID`/`SessionID` 立刻作废 |
| "能不能只保持会话、不重新登录" | **协议上没有这条路**：没有可跨连接携带的 session token / resume 机制，新连接必须重新认证 + 重新登录 |
| 那该做什么 | 目标不是"保持会话"，而是 **① 永不处于无会话状态；② 会话重建是原子的、可观测的、幂等的；③ 断连期间的业务状态靠对账恢复，而不是靠重发** |
| 现在的问题 | 会话有效性是**用两个布尔推出来的**（`_hadLoggedIn && !_socketAlive`），依赖 SDK 回调的相对顺序；任何一次事件丢失/乱序，闸门静默失效 → 报单发在未认证的连接上（2026-10-29 现场：前置持续记 `非预期帧（等认证）`） |

一句话：**会话不可能"保持"，但"无会话窗口"可以做到零**——把重建做成状态机的一条边，把恢复做成对账，而不是散落在各处的 if。

## 1. 概念先对齐（这是很多困惑的根源）

| 层 | 是什么 | 生命周期 | 断了以后 |
|---|---|---|---|
| **TCP 连接** | 到前置的一条 socket | 秒级到小时级；会被前置主动关（240 帧策略）、被网络掐 | 客户端可重连，**但什么都不继承** |
| **认证（ReqAuthenticate）** | 用 AppID/AuthCode 证明"这个客户端软件被授权" | **per-connection**，一次连接一次 | 必须重做 |
| **登录（ReqUserLogin）** | 用账号/密码建立投资者会话 | **per-connection**，返回 `TradingDay / FrontID / SessionID / MaxOrderRef` | 必须重做，且拿到的是**新的 FrontID/SessionID** |
| **会话（Session）** | 柜台侧持有的一条投资者会话，客户端只持有标识 | 柜台回收（断连即回收；柜台侧还有"会话未过期不许重登"的窗口） | 不可恢复，只能新建 |
| **业务状态** | 持仓、资金、在途报单、成交、行情订阅 | **跨连接存在**（在柜台里） | 必须重新查询/重建，不能假设 |

所以"重新登录"不是多余动作，它是**唯一能让新连接具备下报单能力的方式**。真正的缺陷不是"我们又登录了一次"，而是**某条路径上一次都没登录就发了单**。

## 2. 我们的代码为什么会被这件事咬

四处机制（都在 `src/Ctp.Net.Client/CtpSessionService.cs`）：

| # | 机制 | 后果 |
|---|---|---|
| 1 | 会话有效性 = `_hadLoggedIn && !_socketAlive` 推导（`:429`） | 闸门只在"管理层的 Disconnected **先于** Connected 到达"时成立。SDK 内部自动重连时，两个回调来自不同线程；任何乱序/丢失（或 `ReconnectAsync` 撞上 `_reconnectLock`（`:493`）直接 return、或 `_cachedTraderCreds` 为空）都让"该重登"这件事被静默跳过 |
| 2 | 登录结果 `FrontID/SessionID` 只被当作"展示用"，没有当作会话身份 | 无法回答"我现在发单用的会话，是不是已经登录过的那条" |
| 3 | `OrderRef` 是 `CtpTrader` 实例内的内存计数器，登录时用 `MaxOrderRef` 初始化（`ctp-net-core/.../CtpTrader.cs:70/199/221`） | 重建实例就重置；进程重启则完全依赖柜台回的 `MaxOrderRef`。没有"本地高水位"作为第二保险 |
| 4 | **没有在途请求账本** | 断连瞬间发出的报单/撤单，既不知道柜台有没有收到，也不在重连后对账 → 撤单静默丢失（54,738 张僵尸单就是这么来的） |

补充：`ReconnectAsync`（`:490-561`）本身是对的——摘事件、Dispose 旧实例、新建 `CtpTrader`、`LoginAsync`（内部就是 Init → 等 FrontConnected → 认证 → 登录，`CtpTrader.cs:165-205`）、恢复行情订阅。问题是**它由布尔闸门触发，而不是由"每个新连接都必须重建"这条不变量保证**。

## 3. 目标形态：会话状态机 + epoch

```
                 ┌──────────────┐  Init/连接失败/超时
                 │ Disconnected │◄──────────────┐
                 └──────┬───────┘               │
             前置 TCP 连上（每个新连接都算）        │
                        ▼                       │
                 ┌──────────────┐  认证失败      │
                 │  Connected   │───────────────┤
                 └──────┬───────┘               │
             ReqAuthenticate 成功                │
                        ▼                       │
                 ┌──────────────┐  登录失败      │
                 │ Authenticated│───────────────┤
                 └──────┬───────┘               │
             ReqUserLogin 成功（拿到新 FrontID/SessionID）
                        ▼                       │
                 ┌──────────────┐               │
                 │   Ready      │───────────────┘
                 └──────────────┘  断线 / 主动重建 / 会话被踢
```

四条不变量（写进代码注释，比什么优化都重要）：

1. **`FrontConnected` 事件 = 新 epoch**：无条件重建（认证+登录），不看任何"以前登录过"的布尔。
2. **只有 `Ready` 并且 `epoch` 匹配时才允许下报单/撤单**；否则排队或直接拒绝（要显式报错，不能静默丢）。
3. **epoch 就是登录回来的 `(TradingDay, FrontID, SessionID)` 三元组**，随每条报单/回报一起记，用于对账。
4. **每条边幂等**：重复的 `FrontConnected`、重复的 `ReconnectAsync`、重复的登录应答都不能产生第二条会话。

状态机的实现要点：

- 用**显式状态字段**（枚举）+ **每状态超时**（连接 15s / 认证 15s / 登录 15s，与现有 `CtpTrader` 一致），而不是靠 TCS 的相对顺序推断；
- 重连互斥用"目标状态 + 版本号"而不是 `SemaphoreSlim.WaitAsync(0)` 直接 return（后者会把"另一个重连正在跑"和"我该重连"混为一谈，等那次跑完就没下文了）；
- 所有 native 回调先投递到单线程队列再处理（现有 `Task.Run` 已经够用，但状态迁移必须串行化）。

## 4. 恢复而不是重发

断连时"哪些事悬着"必须能枚举，否则重连后只能瞎猜。

### 4.1 报单：intent log + 终态

- 发 `ReqOrderInsert` **之前**落一条 `intent`（键 = `epoch + OrderRef`，内容 = 合约/方向/开平/价/量），拿到 `OnRtnOrder`（或 `OnRspOrderInsert` 错误）后写终态；
- 断连时所有 `intent` 未终态的单标 `unknown`；
- 重连后 `ReqQryOrder`（按交易日/合约）拉全量，按 `OrderSysID` 与本地 intent 对齐：**柜台有的就是活的**（继续跟踪/撤），**柜台没有的就是没进去**（按策略决定补单还是放弃，绝不盲目重发）；
- 这一步是"撤单静默丢失"的根治手段——不是让撤单不丢，而是**丢了能发现**。

### 4.2 撤单：跨会话必须用柜台侧标识

协议事实：撤单请求既可以用 `OrderSysID`，也可以用 `(FrontID, SessionID, OrderRef)` 三元组。**后者在重连后已经换了**（新会话新编号），所以：

- 从 `OnRtnOrder` 起就记录每条报单的 `OrderSysID`（以及它诞生时的 epoch）；
- 重连后的撤单**优先用 `OrderSysID`**；`OrderSysID` 缺失时用"旧 epoch 三元组"（要留着旧的那个），并把这个分支记进日志——它是可疑路径；
- 撤单本身要幂等：柜台回"订单不存在/已终态"应当视为成功（目标状态已达成），不要当失败重试到死。

### 4.3 行情订阅：desired set 幂等重订

订阅是 per-connection 的。维护一个"期望订阅集合"，每次 `Ready` 后整集重订（幂等），而不是靠"上次订了啥"的增量。这条现在已基本成立（`_cachedSymbols` + `ReconnectMdAsync`），补一条：**重订失败要重试并告警**，否则界面表现为"连上了但没行情"。

### 4.4 持仓/资金：重连后强制刷新

柜台侧是真值，客户端缓存一律作废。重连后立刻刷一次，并把"日志里报的持仓"和"查询得到的持仓"做一致性检查（今天的 43/36 vs 11254/9226 就是没人做这个检查才漂了那么久）。

## 5. 让"重建"不再打断交易：三条路（按性价比排序）

### A. 消除 240 强制断连（根因）

前置为了绕开 F0 推送序号 1~251 的上限，累计 240 条就关连接（`ctp-net-front/src/Ctp.Net.Front/CtpFrontSession.cs:198`）。这把"会话重建"的成本摊到了**高频路径**上——活跃行情几秒一次。三个方向，从易到难：

1. **挪到安全点**：确实要断，就在"无在途报单 + 无待发撤单"的时刻断（前置与客户端协商，或客户端自己主导），而不是凑够 240 就掐；
2. **客户端主导的主动重建**：客户端自己数私有流帧，在接近上限时（如 220）主动走安全点重建——退役的 5c6f9ff 试过在客户端硬算，失败原因是**计数在 SDK/前置内部，客户端数不准**；若前置在每条回报里带上"本会话已推帧数"（这是前置自己的计数，一定准），客户端就能精确地在安全点重建；
3. **协议层续号**：如果 240-251 那段"裸值/转义对"能被 SDK 接受，就不再需要断连——需要抓包验证，成本最高。

### B. make-before-break（双连接交接）——"永不无会话"的真正形态

既然会话不能续，那就**重叠**：新连接先建好（认证+登录成功、拿到新 epoch）→ 切流量 → 再关旧连接。代价与风险：

- 柜台是否允许同一投资者**同时**存在两条会话？多数柜台会把新登录当作"重复登录"踢掉旧会话，或被旧会话挡住直到超时。**必须在 SimNow / 真实柜台实测**（见 §9 实验 1）；
- 若柜台按"新踢旧"处理，交接顺序就要反过来：新登录成功的一瞬间旧会话已死 → 立刻把在途账本标记 unknown → 用新会话对账。这依然比"断了才重建"好，因为**中间没有无会话窗口**。

### C. 退避与快速重连

- 重连必须是**指数退避 + 抖动**（0.5s → 1s → 2s … 上限 30s），并记录每次尝试的原因与结果；
- 重连"太快"可能被柜台以"会话未过期/重复登录"拒绝——这是**正常路径**，不是故障，要计入状态机的 `WaitingForSessionExpiry` 之类状态，而不是无限重试刷日志。

## 6. 可观测性（缺了它，上面全部白做）

`two-bots-live-market.md` §2.7 已经说过：生产 bot 的 stdout 被关掉之后，只能靠前置日志反推。会话层至少要有：

| 信号 | 形态 | 用途 |
|---|---|---|
| 极简会话日志 | 只记 `连接 / 认证 / 登录 / 断开(reason) / 重建 / Ready / 会话被踢`，按天轮转 + 单文件上限 | 判定"到底有没有重登"（本次事故就是这里没有证据） |
| `session_age` / `epoch` | 心跳或日志里带上 | 判断"是不是刚重建过" |
| `reconnect_count` / `relogin_latency_ms` | 计数 + 分位 | 240 断连的实际频率与重建耗时 |
| `in_flight_unknown` | 断连时未终态的单数 | 直接量化"可能丢了多少" |
| `orders_rejected_unauthenticated` | 前置侧的 `等认证` 计数（前置已有）与客户端侧配对 | 这条一旦非零就是本类缺陷复发 |

## 7. 落地顺序

| 优先级 | 事项 | 验收 |
|---|---|---|
| **P0** | 会话状态机 + epoch；`FrontConnected` 无条件重建；`Ready` 前禁止下单（显式拒绝不打静默丢） | 人为掐断前置 20 次，`orders_rejected_unauthenticated = 0`，每次断连后 2s 内回 Ready |
| **P0** | 极简会话日志（几十 KB/天） | 能从前置+客户端两份日志还原每一次会话的生死 |
| **P1** | 在途账本 + 重连后 `ReqQryOrder` 对账；撤单改用 `OrderSysID` | 断连期间发起的撤单，100% 在重连后落地或明确标记失败 |
| **P1** | `OrderRef` 本地高水位（落盘到既有 `SqliteCtpConfigStore`），取 `max(本地, MaxOrderRef)+1` | 进程重启后报单 ref 不重复、不回卷 |
| **P2** | 240 断连挪到安全点（方案 A2：前置回显本会话帧数，客户端择机重建） | 活跃行情下连续 30 分钟无"凑数掐断" |
| **P2** | 行情腿与交易腿**独立重连**（互不牵连），并做订阅幂等重订 | 只掐行情腿时不触发交易腿重建 |
| **P3** | make-before-break 交接（先做实 §9 实验 1） | 切换期间 `Ready` 覆盖率为 100% |
